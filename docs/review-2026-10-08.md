# PixelPets 当前版本 Review、进度与下一阶段规划

审查日期：2026-10-08（北京时间）。审查基线：`5746ebd54b6b5b28a99f96c8f11d4753ce194ede`。

本报告回答：现在能否在链上运行、玩家有哪些前置条件和卡点、可以如何优化、语言与多端做到哪一步，以及接下来如何交付。结论依据当前源码、正在运行的本机服务、本轮测试、浏览器观察及已有真实本地链证据。没有执行新的公共链部署或主网交易，也没有用测试钱包代替真人钱包验收。

## 1. 先说结论

**协议核心已经在真实本地 Solana 链上执行过；当前打开的游戏仍是链功能关闭的本机版本，不能向普通玩家宣传为“已经上线的链游”。**

养成主要由 Godot 客户端和服务端数据库承担，链记录可转移资产、成长检查点与交易结算。现有设计是链上资产与链下玩法结合的游戏，不是每次喂食都执行链上交易的全链游戏。

可以演示免费领养、照顾、出游、成长、卡册和日记；合约有领取、成长登记、托管交换、买卖和取消的执行证据。面向玩家的上架、购买、交换、赠送和成交后继续养成，尚未连成完整流程。

**当前最优先的产品问题是：玩家换设备后能否找回伙伴、购买后是否真的成为可继续养成的新主人，以及普通人能否通过一个网址开始玩。** 国际化、移动输入与首屏加载应和这些工作一起进入下一轮，而不是先增加 AI、硬件或更多宠物种类。

## 4. 玩家真正会遇到的卡点

### 4.1 新玩家想先玩：网址和存档比钱包更优先

现在的网址指向开发者本机，其他人的电脑或手机打开自己的 `127.0.0.1` 无法访问这台开发机。把 EXE 单独发出去也不够，它默认访问本机 API，仍需运行服务或另行配置公共 API。

免费养成当前不要求钱包，也不要求买 SOL，这个顺序应保留。公开试玩的目标体验应该是：打开 HTTPS 链接 → 免费领养 → 得到一次有反馈的互动 → 在主动保存/收藏/交换时再解释账号和链上身份。

游客令牌目前保存在 Godot `user://session.cfg`；Web 中依赖浏览器持久存储。清站点数据、换浏览器、换设备可能失去这张访问凭据。数据库保留宠物，并不意味着用户仍能访问它。

改进：提供独立的“找回已有伙伴”入口；明确哪些档案只保存在当前游客身份下；需要长期保存时提供可靠恢复方式。不要把钱包连接按钮当作已经完成账号系统。

### 4.2 已经绑定钱包的老玩家：换设备会被拒绝

[repository.ts](../server/src/repository.ts) 第 145–160 行将钱包与游客 `user_id` 一对一绑定。第 153–154 行在原钱包遇到新游客身份时直接拒绝。使用临时 Ed25519 钱包和内存库已复现：

1. 游客 A 创建档案并完成钱包 W 的消息签名验证，成功。
2. 新设备创建游客 B，使用同一个 W 完成真实消息签名。
3. 验证返回 409 `WALLET_ALREADY_LINKED`；B 仍看不到 A 的宠物。

同一游客切到另一个钱包也会触发绑定冲突。现有拒绝逻辑避免静默合并身份，是必要保护；缺口是没有提供明确的恢复与切换流程。

改进：新增钱包恢复挑战与验证，成功后恢复原用户会话；只凭钱包地址绝不能恢复。游客新档案与旧钱包档案冲突时，应让玩家明确选择保留/迁移策略，不能自动覆盖。验收必须覆盖另一浏览器、清缓存、会话过期、钱包切换、拒签和重放攻击。

### 4.3 玩家想交易：资产与养成档案还没有同步转移

合约与 SDK 支持转移资产，但 [app.ts](../server/src/app.ts) 第 76、102–103 行和 [repository.ts](../server/src/repository.ts) 的宠物查询、照顾及改名按 SQLite `user_id` 授权，没有自动依据链上最终所有者重分配档案。

因此，**即使在合约或外部工具完成转赠，接收人也不会自动获得游戏内可继续照顾的伙伴，原账户的链下操作权限也没有随转移自动撤销。** 链上 checkpoint 会再次检查真实所有者，所以这不表示旧主人能绕过链上所有权；问题在于链下产品状态与链上资产脱节。

改进：以网络、程序、资产地址确定唯一资产身份；在读取或管理已登记宠物时核对最终所有权，完成可重试、幂等的档案同步。托管期间应有明确状态，不能把 Offer PDA 当作普通新玩家。新主人接收宠物后继续成长，旧主人停止管理；私人账号日记不应不加区分地转交给买家。

当前免费领养上限为 3 只，接收外部资产时也要有明确规则。建议把免费领养额度与已拥有资产的展示/接收分开，避免玩家链上购买成功后因为档案容量而看不到宠物。

在这一点完成前，不开放真实玩家付费交易。

### 4.4 玩家连接钱包：目前仍需要懂一些链的概念

当前网页要求钱包支持 Wallet Standard、相应 Solana 网络与消息签名；交易还要支持所需的交易签名能力。没有发现钱包时，仅显示安装扩展或使用钱包内置浏览器的文字说明，没有完整的手机打开入口、二维码或回跳恢复体验。

优化分两层：

- 产品层：只在需要链上行为时连接钱包；先解释“登录签名不花钱”，再在真正提交交易前展示“本次操作、网络、接收地址、预计总支出、取消选项”。
- 兼容层：先验证一组明确的桌面钱包与手机钱包环境，给出可操作的打开指引；通过后才列入支持名单，不笼统写“支持所有 Solana 钱包”。

免费照顾继续在链下完成，成长可以在明确的里程碑保存为 checkpoint，避免每次照顾都要求签名。现有机制已有这个方向，不需要为了“链游”而增加无价值交易。

### 4.5 玩家在钱包里看宠物：图片与成长记录需要明确关系

当前真实链测试使用测试 URI，未证明普通钱包能够读取正式图片。领取时复制 Edition 的名称/URI，并采用不可变元数据规则；后续 checkpoint 更新成长记录，并不会自动改写普通钱包显示的图片。

应在发行前选定展示规则：第一版可以使用固定的角色身份图，在游戏/只读展示页依据可核验的成长记录呈现当前像素形态。若承诺钱包内也会动态换图，就需要单独设计并验收相应元数据机制，不能把 immutable URI 当作已经具备这一能力。

正式发布需保存三物种的 JSON、像素图片、URI 和内容摘要，实际取回验证，并检查离开游戏服务后仍可读取。这一验收也决定未来硬件能否可靠地显示同一位伙伴。

不要用“单笔网络费很便宜”替代费用预览。现有领取还涉及资产相关账户资金和协议费用，本地证据中的数值只代表那次测试，不是主网报价。是否提供首次操作补贴，可以在基本流程完成后评估：服务端严格限制允许的指令、每人额度和总预算，保留玩家对资产操作的确认，并明确这是运营成本，不是收益来源。

### 必须正视的适配缺口

1. **手机文字输入。** [export_presets.cfg](../game/export_presets.cfg) 的虚拟键盘选项为 false，领养和改名却使用 Godot `LineEdit`。默认名字让玩家仍有可能跳过输入，但手机取名可用性尚未得到保证。应启用并实测；必要时使用 HTML 原生输入框，处理中文组合输入。同步修改会重写该配置的 [build.ps1](../tools/build.ps1)，不能只手改导出产物。[Godot 虚拟键盘选项](https://docs.godotengine.org/en/4.5/classes/class_editorexportplatformweb.html#class-editorexportplatformweb-property-html-experimental-virtual-keyboard)
2. **国际化范围。** 游戏、钱包桥、交易提示以及服务器日记存在硬编码文案，没有翻译资源或语言切换。日记宜使用事件类型和参数进行本地化，昵称保留玩家输入。钱包签名挑战的准确原文保持可核验，旁边提供本地化解释。
3. **触摸、安全区与弹窗。** 当前固定边距，没有安全区适配；四主页宽度通过不代表键盘弹起、长地址、钱包弹窗及底部手势区域可用。
4. **页面语义。** 当前生成 HTML 为 `lang=en`，主体却是中文；页面缩放被禁用。钱包原生 dialog 有键盘焦点基础，但可补可访问名称。应在可重建模板中修复；本轮浏览器的可访问树主要只暴露 canvas，不宣称读屏支持已完成。

Godot 4.5 的 Web 导出依赖 WebAssembly/WebGL 2.0，单线程导出适合当前项目，也降低了跨源隔离要求；移动端仍需单独检查兼容性与性能。框架支持某个平台不代表本项目已经验收该平台。[Godot Web 导出说明](https://docs.godotengine.org/en/4.5/tutorials/export/exporting_for_web.html)

| 公开交易前 | 钱包恢复、成交后档案转移、玩家交易接口未完成 | 见第 4 节和第 9 节，全部通过才开放玩家交易 |
| 手机公开演示前 | 缺少软键盘、真机输入和移动钱包验收 | Android/iOS 各至少一台真实设备，覆盖中文输入与钱包往返 |
| 体验优化 | 静态文件未压缩，全部 `no-cache`；没有条件缓存处理 | 生产静态层压缩，HTML 短缓存，版本资源长缓存；验证升级不会混用旧包 |
| 运行稳定性 | `/health` 在启用链后调用多项链配置核验；单 RPC 超时不等于整个流程有总时限 | 拆分轻量存活检查和限时就绪检查；短时缓存就绪结果，交易前仍严格核验；RPC 故障不影响免费照顾 |
| 构建复现 | `-Target Web` 也要求 Windows/debug 模板；新克隆仍需手动准备模板 | 按目标检查模板，提供明确版本与路径；在干净克隆中跑测试和 Web 导出 |
| 数据增长后 | 游客会话、事件与完整幂等响应长期累积 | 定义保留/归档策略、容量监控；不能简单删除去重依据导致重复奖励 |

现有保护值得保留：真实消息验签、请求幂等、服务端时钟、金额整数精度、共同签名验证、原始交易重建、最终状态核对、待确认交易持久化、SQLite 租约及失效写入拦截。后续优化不应绕开这些机制来换取看似更快的演示。

## 8. 产品层面的取舍

当前陪伴与收集原型已经有可展示的基础，但“玩家为什么持续回来、为什么付费”仍需验证。自动测试和成功交易都不能证明消费需求。

- 免费用户的收益是轻松陪伴、短互动反馈与收藏进展。保留无需钱包的开始方式，不让行情或签名打断日常照顾。
- 付费用户应为可见、可理解的内容或服务付费，例如明确外观、主题套装、定制展示或想收藏的特定宠物；先验证一个清晰付费对象，再扩充 SKU。
- 部分玩家赚到钱的来源应是其他玩家愿意消费的需求。平台可在真实成交中收取明确费用；当前没有真实成交额、收入或已验证的留存数据，不能写成商业结果。
- 独特价值需要积累在原创美术、可验证的成长经历、收藏目标和玩家关系中。区块链提供资产持有与转移能力，不能单独证明不可替代性。
- AI 与像素硬件保留为后续实验。AI 先负责表达，不能决定资产或收益；硬件先展示同一份档案，不存玩家助记词。先验证玩家是否会主动回来，再承担硬件供应与多端维护成本。

首批可邀请 5–10 名目标玩家做有观察记录的试玩。这是建议样本规模，不是已完成测试。记录首次互动所需时间、未获帮助时能否找回档案、钱包在哪一步被放弃、次日是否主动回来，以及愿意为哪个具体内容付款；把意愿访谈与真实支付行为分开记录。

## 9. 下一阶段的研发顺序与验收标准

以下是单人开发的粗估，属于规划而非工期承诺；不包含采购、等待外部服务、独立审核或比赛审批。阶段可能重叠，当前没有重新确认比赛截止时间，不沿用早期讨论中的“剩余天数”。

| 阶段 | 工作内容 | 完成标准 | 初估 |
| --- | --- | --- | --- |
| A：可恢复的公开免费试玩 | 钱包恢复与游客冲突规则；HTTPS、代理限流、持久磁盘和备份；干净克隆校验 | 两个外部设备能玩；换设备后真实签名找回同一档案；多人不共享误限流；服务重启/备份恢复后进度一致 | 2–4 人日 |
| B：公共 Devnet 身份闭环 | 发布正式像素元数据；部署/初始化；真钱包领取和成长登记；状态与费用说明 | 外部浏览器实际签名，最终资产/记录一致；拒签、错网络、余额不足、断网、刷新及交易过期均可恢复 | 2–3 人日 |
| C：玩家交易闭环 | 固定价上架/购买/取消，然后接入交换与赠送；资产所有权和养成档案同步 | A 的宠物交给 B 后，B 能继续照顾，A 不能再管理；托管、过期、取消与失败均不丢资产；资金明细一致 | 3–5 人日 |
| D：中英与手机体验 | 双语文本、日记本地化、软键盘、钱包打开/回跳、安全区、压缩缓存 | 中英均能完成同一全流程；Android/iPhone 真机可输入并签名；长文字/地址不裁切；记录弱网加载和恢复 | 2–4 人日，可与前述阶段交错 |
| E：主网小范围发布 | 独立安全复核、构建/部署摘要、权限安排、监控、预算、事故演练 | 测试网门槛全部满足；发布参数可审查；完成主网小额实际验收、备份恢复和暂停取回，再逐步扩大 | 外部复核后另估 |

A 不要求把钱包作为免费游戏门槛；它解决的是自愿绑定后可恢复。C 先完成一种交易方式是实现顺序，完整范围仍包括购买、交换、赠送与撤销。D 不是“全部原生平台同时上线”：黑客松首发采用桌面和手机 Web，Windows 保留养成体验；原生移动、AI 与硬件在主流程稳定后单独排期。

下一轮应优先从 **钱包恢复与所有权同步的数据模型** 开始，再接公开服务和玩家交易。如果先把买卖按钮打开，玩家买到资产却无法继续养成，会破坏产品的核心承诺。

## 10. 必须通过的整体验收场景

1. 新玩家在外部 HTTPS 页面无钱包领养、取中文/英文名字、照顾并获得服务端确认，刷新后仍在。
2. 玩家自愿绑定钱包，退出后在另一浏览器/设备通过真实签名找回原档案；不能用相同地址文本冒领。
3. 同一宠物重复点击领取、断网后恢复、服务重启后恢复，只产生一个正确资产；成功提示必须等待对应最终确认。
4. A 上架宠物，B 购买；链上资金和所有权正确，B 在游戏内获得管理权，A 失去管理权；原私人日志不意外公开给 B。
5. 完成一次双向交换及一次直接赠送，同步双方档案；托管期间不允许不一致的成长更新。
6. 用户取消签名、切错网络、切账号、余额不足、报价过期、RPC 不可达时，都有可理解且可重试的状态，不显示虚假成功。
7. Android 与 iPhone 的真实浏览器/钱包环境完成输入、触摸、回跳和恢复；只通过桌面尺寸模拟不算完成。
8. `zh-CN/en` 覆盖以上所有成功/失败路径；刷新后语言不变，长英文不裁切，钱包和游戏语言一致。
9. 模拟服务中断，从一致性备份恢复后能继续处理原待确认请求，不多发宠物、不重复奖励。
10. Devnet 与主网的页面标识、余额、地址、元数据及部署版本明确区分；主网发布前另做实际验收。
